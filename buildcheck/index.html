Buildcheck

Every ad checked against the plan, with evidence, before it spends.

Buildcheck compares every ad in the account with the media plan and flags what doesn't match: a wrong budget, a wrong link, a missing headline. Each finding shows the plan value, the export value and the rule that decided it. It's in production on Meta, where a media team used it on live batches, and it turned a four-day, four-person review into one 20-minute run.

How it works

Five steps, from the media plan to the QA report. Each has fixed inputs and a fixed output, so a batch can be run again until it's clean.

A paid social build is a tree of settings: a few campaigns, a dozen ad sets, dozens of ads, each with 30 to 100 fields. Before Buildcheck, the plan was typed by hand and a senior person re-checked every row against Ads Manager. Errors that slipped through spent money.

  1. Paste the media planOne row per buy, every platform: budget, flight, market, objective, optimization, funnel, suppression. This is the record of what was bought.MEDIA_PLAN
  2. Expand it into the buildName the ad sets on the build grid, and one menu click generates the campaign, ad sets and ads with derived values filled in. Running it again adds nothing twice.BUILD_ADSETSone click
  3. Clear the gateNine checks per line (market, buy type, flight start and end, budget within tolerance, objective, optimization, funnel, suppression) before anyone opens Ads Manager.PLAN_CHECK
  4. Build and exportBuild in Ads Manager, paste the campaign, ad set and ad IDs back, and pull the bulk export. The workbook's feeds resolve inheritance and translate labels into the platform's vocabulary.QA_EXPORT feedsAds Manager
  5. Run the engineThe feeds and the export go to the AI engine. It returns a QA report with a gate, failures with evidence, reviews, human checks and proposed rule changes, plus a findings block to paste back into the workbook.QA reportRUN_REGISTER

New to paid social?

A build is a tree. Each level has its own settings and its own export columns, so the engine runs a different set of checks at each level. At the ad level the checks also depend on the ad type: an uploaded video, a boosted post from the brand's own page, or a creator's partnership post.

Keeping the AI honest

Being good with AI isn't prompting well. It's deciding what the AI is allowed to conclude, what it must show, and what a human keeps.

How I work with AI

Write the rules before the prompt

I didn't ask an AI to “check the campaign”. I wrote the rulebook first: what counts as proven, what a blank means, what it must never invent, which ad type gets which checks. The AI gets those rules as versioned reference files, not chat instructions.

Make it show its evidence

Every finding cites the plan value, the export value and the rule that decided it. Anything unverified is a review, not a failure. Anything new is a proposal a human accepts. A report you can't audit is an opinion.

Pair on the build, own the outcome

Claude wrote the build and test scripts to my spec. I owned the architecture, the rules, the test plan, the rollout and every changelog row. When a run got something wrong, the fix went into the rules and the test fixtures, not into memory.

Ship it to real people

The skill was shared across the organization and used by a media team on live batches. That feedback loop produced eleven releases in twelve days. A manager's “this doesn't read as auto-fill” became the gray-cell design two versions later.

Six principles that box it in

An AI that reads a 100-column export and writes a confident report is dangerous unless it's boxed in. Each of these was written after a real run got something wrong.

  1. Proven or unproven.Every mapping from a planner's label to a platform value carries a proof status, earned from a real export. A mismatch on a proven rule is a FAIL. On an unproven rule it can only be NEEDS REVIEW, so the engine can't fail a build on a rule nobody has verified.
  2. A blank is never compared.Blank means inherit or not specified, never “should be empty”. The feed resolves inheritance before the run, so the engine compares values, not intentions.
  3. Never invent.If the export preset leaves out a column, the checks that need it read “column absent”, and the report says so once, at the top. No value is inferred from a neighboring column, and no ID, file name or handle is ever guessed.
  4. Evidence by machine name.Every finding names the plan field, the export column, the plan value and the export value, word for word. Never a column letter or a cell color, so a report stays true after columns move.
  5. Proposals, never silent changes.Anything new the run sees, like a vocabulary value or a mapping now proven, becomes a changelog proposal for a human to accept. The rules of record live in the workbook and the skill files, never in the model's memory.
  6. One finding, not a thousand.An error repeated across every ad in an ad set is one finding with a count, one card and one fix. The report stays readable and the fix stays obvious.

Platforms

One media plan holds every platform's lines, and each line is checked in the workbook for its platform. The tabs, feeds and engine stay the same. Each platform brings its own export contract, vocabulary and naming profile.

Meta

In production on Facebook and Instagram

  • Uploaded creative, boosted posts and creator partnership ads, each with its own checks and identity model.
  • Placement buckets (feed, story, reels, explore), so one 9:16 file across three placements is expected, not flagged.
  • Budget type verified by which export column is filled. Delivery intent mapped to status. Times compared in the account's time zone.

TikTok

Built on the same architecture

  • Campaign, ad group and ad, with Business Center identities and Spark Ads (creator and brand posts) as the existing-post case.
  • TikTok's own formats handled in the feed: toggles that export blank when off, dates as yyyy/m/d HH:mm, amounts with cents, pixel labels resolved to website-event codes.
  • Reservation buys never appear in an export, so their rows show as N/A instead of MISSING. 306,000+ formulas, 0 errors.

Next

Designed for, not built yet

  • Pinterest, Google and Snap each need three things the design already keeps separate: an export contract (which columns come back and how they're written), a vocabulary map from planner labels to platform values, and a name-part profile.
  • Everything else stays as it is: the plan tabs, the plan-check gate, the feeds, the report and the register.

What I'd build next

  • Pinterest and Snap profiles on the same architecture: an export contract, a vocabulary map and a name-part profile each, and nothing else new.
  • Catch more at plan time. Extend the nine-check gate to budget type, placements and tracking, so a mistake is stopped before the build instead of found after it.
  • A diff between two exports, so a second QA reads only the rows that changed instead of the whole account.

Read the engineering notes

The workbook

Google Sheets first, with Excel and LibreOffice compatibility checked on every release: 310,000+ formulas recalculated headless to 0 errors. Built for 1,000 ads, 500 ad sets and 300 campaigns per account.

Build and test tooling

Python build scripts regenerate every version from a registry, so nothing is edited by hand twice. A fixture suite of executable rule cases, plus structural checks for row alignment, stale references and changelog conformance, runs before a release ships.

Auto-fill layer

A Google Apps Script menu expands a media-grid line into the build, fills derived values in gray and applies the account profile. Running it again is safe: a second click adds nothing.

Change control

A changelog with the before, after, reason, downstream impact, regression test and the run that validated each change: 180+ entries, and a conformance check that must read YES. Rule changes ship as versioned files, never as edits in chat.

The AI layer

A Claude skill: a skill page, reference files for the run rules, the report spec and known failure modes, an HTML report template and a standing run message. It was first deployed as a shared, org-wide skill and now runs with the workbook uploaded directly.

Real exports, not assumptions

Every mapping was proven against live Ads Manager exports up to 500+ columns wide. The largest end-to-end test reconciled a plan against a 974-row live account export.

About this project

I designed, specified and shipped Buildcheck end to end while working in media operations at a paid social agency.

I owned the architecture, the QA rules and their proof discipline, the test plan and the rollout to the team, and paired with Claude to write the build and test scripts to my spec. It started as a fix for a real problem: a senior team spending days on checks that were mostly mechanical. It became a system: a workbook that knows what it is, an engine that has to show its evidence, and a record of every decision.

Where it fits is in-house social media marketing and strategy. A brand's social team owns organic and paid together, and the paid side is only as good as its operations: how campaigns get planned, built, checked and launched. This project is that discipline, plus the AI and systems fluency to make a small team run like a large one.

Internally, the workbook is known as the Gem Arch Doc, after the agency's term for a campaign architecture document.
