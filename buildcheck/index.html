Buildcheck

Every ad checked against the plan, with evidence, before it spends.

In production on Meta and used by a media team on live batches, it turned a four-day, four-person review into one 20-minute run.

How a batch moves through it

A paid-social build is a tree of settings — a few campaigns, a dozen ad sets, dozens of ads, each with 30–100 fields. Before this system the plan was typed by hand and every row was re-checked by a senior person against Ads Manager; errors that slipped through spent money.

Buildcheck runs a batch through five moments. Each has fixed inputs and a fixed output, so the same batch can be re-run until it is clean.

How I work with AI

Being good with AI is not prompting well. It is deciding what the AI is allowed to conclude, what it must show, and what a human keeps.

Write the rules before the prompt

I didn't ask an AI to "check the campaign". I wrote the rulebook first — what counts as proven, what a blank means, what it must never invent, which ad type gets which checks — and gave the AI those rules as versioned reference files, not chat instructions.

Make it show its evidence

Every finding cites the plan value, the export value and the rule that decided it. Anything unverified is a review, not a failure. Anything new is a proposal a human accepts. A report you can't audit is an opinion.

Pair on the build, own the outcome

Claude wrote the build and test scripts to my spec; I owned the architecture, the rules, the test plan, the rollout and every changelog row. When a run got something wrong, the fix went into the rules and the fixtures, not into memory.

Ship it to real people

The skill was shared org-wide and used by a media team on live batches. Eleven releases in twelve days came from that feedback loop — a manager's "this doesn't read as auto-fill" became the grey-cell design two versions later.

How the AI is kept honest

An AI that reads a 100-column export and writes a confident report is dangerous unless it is boxed in. These are the principles that box it in — each one was written after a real run got something wrong.

Proven or unproven

Every mapping from a planner's label to a platform value carries a proof status earned from a real export. A mismatch on a proven rule is a FAIL; on an unproven rule it can only be NEEDS REVIEW. The engine cannot fail a build on a rule nobody has verified.

A blank is never compared

Blank means inherit or not specified, never "should be empty". Inheritance is resolved in the feed before the run, so the engine compares values, not intentions.

Never invent

If the export preset lacks a column, that check reads "column absent" and says so once at the top. No value is inferred from a neighbouring column, and no ID, file name or handle is ever guessed.

Evidence, by machine name

Every finding names the plan field, the export column, the plan value and the export value, verbatim — never a column letter, never a cell colour. A report stays true after columns move.

Proposals, never silent changes

Anything new the run observes — a vocabulary value, a mapping now proven — becomes a changelog proposal for a human to accept. The rules of record live in the workbook and the skill files, never in the model's memory.

One finding, not a thousand

A systemic error repeated across every ad in an ad set is one finding with a count, one card and one fix — the report stays readable and the fix stays obvious.

Under the hood

Under the hood — open the engineering notes

Built to be rebuilt. Every release is generated by script, recalculated to zero errors, regression-tested and logged.

The workbook

Google Sheets first, with Excel and LibreOffice compatibility verified on every release: 310,000+ formulas recalculated headless to 0 errors. Built for 1,000 ads, 500 ad sets and 300 campaigns per account.

Build and test tooling

Python build scripts regenerate every version from a registry, so nothing is hand-edited twice. A fixture suite of executable rule cases plus structural checks (row alignment, stale references, changelog conformance) runs before a release ships.

Auto-fill layer

A Google Apps Script menu expands a media-grid line into the build, fills derived values in grey and applies the account profile. Re-running is safe: a second click adds nothing.

Change control

A changelog with before, after, reason, downstream impact, regression test and the run that validated it — 180+ entries — and a conformance check that must read YES. Rule changes ship as versioned files, never as edits in chat.

The AI layer

A Claude skill: a skill page, reference files for the run rules, the report spec and known failure modes, an HTML report template and a standing run message. First deployed as a shared org-wide skill; now runs with the workbook uploaded directly.

Real exports, not assumptions

Every mapping was proven against live Ads Manager exports — up to 500+ columns wide — and the largest end-to-end test reconciled a plan against a 974-row live account export.

About this project

Designed, specified and shipped end to end by Nicole Glassman while working in media operations at a paid-social agency. She owned the architecture, the QA rules and their proof discipline, the test plan and the rollout to the team, and paired with Claude to write the build and test scripts to her spec.

It started as a fix for a real problem — a senior team spending days on checks that were mostly mechanical — and became a system: a workbook that knows what it is, an engine that has to show its evidence, and a record of every decision. Internally the workbook is known as the Gem Arch Doc, after the agency's term for a campaign architecture document.

Where this fitsIn-house social media marketing and strategy. A brand's social team owns organic and paid together, and the paid side is only as good as its operations — how campaigns get planned, built, checked and launched. This project is that operating discipline, plus the AI and systems fluency to make a small team run like a large one.
